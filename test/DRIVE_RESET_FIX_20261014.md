# 驱动器故障复位修复

## 已确认的移植缺陷

原版 Check_Driver_Error 发布轴报警 30..33；移植后的 alarm_poll_drive_errors
只更新 is_error。check_for_fault 仅在存在系统报警或内部急停时调用
handle_alarm_cmd，因此只有驱动器故障时，HMI_RESET 可能没有进入 HAL 清错入口。
PLC 此时仍因 is_error 拉低 F0.6，阻断 M29 握手。

## 本次修改

- 恢复 X/Y/Z/SP 的 ALARM_AX 30..33 发布与删除。持续故障每拍重申，复位清库
  不能把尚存的驱动器故障隐藏起来；日志只在故障码或故障判定变化时打印。
- Fault 位或有效 603F 非零均视为故障。轴屏蔽仅抑制轴报警，不抹掉故障标志；
  快照读取失败保留先前故障状态。
- 保留四轴 HAL 非阻塞复位和急停优先。请求错误立即报告，不忽略返回码。
- HAL 结束复位后，还须确认四轴反馈可读、Fault 清除、有效故障码为零。
  不支持故障码反馈的设备按状态字确认，不要求其提供不存在的 603F。
- 外层以单调时钟限制为六秒，覆盖残留故障码、请求失败、快照缺失等无法收口
  的情况；HAL 自身的默认五秒超时仍有效。超时报警 131 并禁止恢复使能，
  下一次明确复位才解除该闭锁。PDO 已停止时仍由原有总线错误通道报告。
- 正常期间仅驱动器故障轴禁止使能；无关系统报警不改变既有使能策略。

未修改 HAL 库、路径规划、PLC 梯形图，也未把 F0.6 强制置成健康。
这不是对 0xFF43 厂商含义或其可软件清除性的判断。

## 现场验收口径

使用本次构建的 bin/cnc_rt。故障存在时应看到对应轴报警；按复位后，只有
Fault 与有效故障码均消失才报告复位完成，健康反馈 F0.6 才恢复。
若仍为 0xFF43，应保留轴报警并出现复位超时，不能靠清软件标志继续运行。
131 的界面文字依赖 HMI 报警文本表，RT 日志会明确说明失败原因。
