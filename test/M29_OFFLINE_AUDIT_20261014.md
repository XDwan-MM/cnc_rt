## 后续修复状态（2026-10-14）

以下主体保留最初对照记录，不代表当前代码仍有相同缺陷。
轴报警/复位链已修复，见 DRIVE_RESET_FIX_20261014.md。
HAL 05c6d76 已修复定向旧高电平误完成，并同步到 RT 静态库：每轮提交控制字后
须先见 done mask 全低，再见高且满足最短延时才置 DONE。延时内的低电平会记录，
请求前的低电平不计入；释放、取消和新请求清空记录，Fault 不作为有效握手。
真正完成后的 DONE 仍保持到释放/取消，与原版保持对准的契约一致。
build_orient_differential.sh 现已改为验收断言，两版都必须输出：

```text
bit10 high for 30 cycles -> still RUNNING
subsequent low -> high -> DONE
```

HAL ASan/UBSan、CTest、RT 主轴/M29/故障复位回归及 Debug/Release 构建通过。
该修复消除可复现的假完成风险，不代表已经证明它是现场所有多转现象的根因。

## 本轮边界

不修改路径规划，不强置 F/G/X/R 寄存器，不更改运动、使能或故障判据。
本轮新增的是可重复的离线对照和独立只读采集工具，不是新的机床修复版本。
参考源为 `../cnc_rt-feature`；移植实现为 `port_work` 和 `../HAL`。

## 已经验证

1. 故障发布链：测试直接调用现版 `alarm_poll_drive_errors()` 和
   `plc_output_axis_status()`。四轴健康时 F0.6=1；逐轴注入有效非零故障码时
   F0.6=0，只有主轴故障才置 F45.0。轴槽没有在这一层互换。
2. 原版 `Check_Driver_Error()` 同样以非零故障码设置 is_error；不是移植版
   新增了“非零故障码阻止攻丝”的条件。现版额外排除了屏蔽轴、不可读反馈、
   无有效故障码的轴，这些差异会使故障标志减少，不能单独解释现版 F0.6 持续为 0。
3. 原版会发布/删除轴报警 30～33，现版这里只更新标志并在变化时打印。
   因此现版确实可能“PLC 已受故障标志阻止，界面却没有对应轴报警”。
   这是反馈缺口，不是故障码为何出现的证明。
4. 现版轴槽 X/Y/Z/SP -> 从站 3/4/5/2；原版驱动器序号 SP/X/Y/Z 再映射回
   RT 轴槽。逻辑映射一致。HAL error_code 来自绑定的 16 位错误码条目，
   读之前清零，再赋入相应轴快照。未在所查路径发现跨轴复制或高字节残留。
5. IO 两个 16 位输入按低字节优先映射 X0～X3，与原版一致；面板从 X4 开始。
   原版先取上一拍 IO 缓存再更新，现版取本拍映像，有一拍时序差异，不能解释
   一个稳定输入长期为 0。物理条目实际绑定仍取决于现场设备和配置。
6. 选定 PLC 回放中，F0.6=0 会导致 G61.0 刚置起就被 R500.3 终止，并按
   500ms 定时器反复重试。F76.3 一直保持高仍可复现，与 10.14-7/8/9 一致。
   这是阻塞机制的复现，不是上游故障来源的最终证明。
7. M29 的 MF/FIN 低电平确认、宽度和 NC 就绪双条件在两版基本相同；
   移植版新增了 30 秒报警。虽然代码注释称“只观察”，setAlarm 会被系统
   报警流程消费，不能视作完全无行为影响。7/8/9 在 30 秒前已经被复位，
   因而该超时不能解释这些日志中先发生的 PLC 请求反复撤销。

## 新确认的移植差异：定向完成判据

`build_orient_differential.sh` 分别编译原版生产 `driver.c` 和现版生产 HAL，
使用隔离的反馈/总线桩，不接机床。相同反馈序列结果如下：

| 输入 | 原版 | 当前 HAL |
| --- | --- | --- |
| 请求后 bit10 持续高 30 拍 | 仍等待 | 10ms 等待期后认定完成 |
| 随后 bit10 低一拍 | 记录本轮开始 | 已完成状态仍锁存 |
| 随后 bit10 高 | 认定本轮完成 | 仍为已完成 |

原版要求本轮观察到低再高；现版只用延时后高电平。若驱动器的旧到速/完成位
持续超过等待期，现版有提前完成的风险。这是已复现的语义差异，但不能据此
断言它造成了 10.14-7/8/9 的 F0.6=0，也不能证明它就是之前多转的原因。
不在 HAL 通用接口里直接改成所有设备必须出现下降沿：原接口只约定延时和
完成掩码，修改会影响从未清零完成位的设备。正式修复应明确该机型的本轮
定向握手契约，并覆盖重复 M19、静止 M19、M29、复位与释放场景。

## 对此前判断的纠正：强制触点

PLC 执行器支持 `LadInstr.state` 强制触点，计算值可以不同于寄存器值。
已离线复现：同一份本地梯形图，强制夹紧触点成立，即使 R1000.3=0，
也能得到 R999.5=1、G70.5=1。因此日志 8 的这组值不能单独证明梯形图版本
不同或 IO 映射错误。现场是否存在强制状态尚不清楚，不能推定有人强制过。
普通梯形图文件和寄存器日志未必保存运行时强制状态，需一起采集。

## 一趟采集安排

工具不需要联网、现场编译或启动额外 RT。将预编译 `rt_site_snapshot` 和
`capture_site.sh` 放在同一个目录。工具仅附加已有共享内存，使用只读映射，
不调用会创建/重置共享内存的 shmInit，不注册为 HMI/RT 客户端。
采集包不包含或替换 RT，不自动运行机床指令。继续使用之前的诊断版 RT
即可；如做原版对照，按已有的部署方式切换。`runtime-libraries.txt` 列出
工具依赖的 Qt5/系统库，工具和当前 RT 在同一构建环境生成。

1. 备份当前能够恢复的原版程序和现场配置。不要修改联锁、参数或强制状态来
   让测试通过。记录当前强制状态即可。
2. 按原有方式启动 RT，保留从启动开始的完整控制台/应用日志。本工具不能
   找回启动前已丢弃的 stdout，不会读取并抢走 HMI 的日志管道。
3. 在确认安全的原测试条件下，执行一次原来失败的单独 M29。卡住时，在复位
   前执行以下命令。不能安全停留就先停止，不以采集优先于安全。

```sh
sudo bash capture_site.sh /实际固件目录 /U盘或本机目录/ported-stuck RT进程号 /实际日志目录
```

第四个参数日志目录可省略，但随后必须补充完整日志。RT 进程号可省略，仅在
恰好找到一个 cnc_rt/cnc_rt_d 时自动选择。输出目录必须是新目录且位于固件
目录之外。采集后保留整个目录，不只取 snapshot.json。

4. 条件允许时，在相同机床、参数、梯形图和输入状态下，按原部署流程运行
   已知正常原版，执行同样程序并采集到另一个新目录。不要同时启动两份 RT。
   不需要为了采集反复跑更多指令组合。
5. 两组都记录程序文本、执行顺序、是否刚启动/复位、实际运动现象，以及
   是否换过配置。无法保持条件一致的地方写明，不把它当严格 A/B 对照。

采集内容包括运行中 RT 二进制、进程路径、内存映射、固件 plc/conf/data、
完整共享内存原始快照（含梯形图/强制触点/寄存器/参数/报警）及 SHA256。
共享内存布局匹配时另生成便于阅读的 JSON；不匹配只保留原始数据，不猜偏移。
快照不锁实时线程，因而不是原子扫描，不能据单个跨字段瞬时组合认定时序错误。
采集目录包含机床程序与参数，应按内部资料保管。

## 当前还不能确认

现有日志没有各轴原始故障码和现场运行时 PLC 数据，因此尚不能在“实际故障、
错误反馈、现场强制/外部写入、部署版本差异”之间唯一归因。当前没有证据
支持忽略 0x603F、强置 F0.6 或伪造 FIN；这些都不是可接受的修复。
